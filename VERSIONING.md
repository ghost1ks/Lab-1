# Політика версіонування

## 1. Модель життєвого циклу: Agile (Scrum)

**Чому Scrum.** Проєкт невеликий, вимоги можуть уточнюватись по ходу роботи, а результат потрібно показувати частинами. Scrum з коротким спринтом дозволяє швидко отримувати робочий результат, змінювати пріоритети й регулярно випускати версії. Waterfall не підходить: змін у вимогах уникнути не вийде, а перший робочий результат з'явився б надто пізно. V-model надмірно формальна для одного розробника.

**Параметри процесу:**
- Довжина спринту: 1 тиждень.
- Планування спринту — на початку (30 хв), демо/review — в останній день, ретроспектива — одразу після review (15 хв).
- Щоденний мікро-стендап для одного розробника замінюється записом у нотатках: що зроблено, що далі, що заважає.

**Артефакти:**
- *Product backlog* — перелік функцій із ТЗ (FR-1 … FR-5), впорядкований за пріоритетом.
- *Sprint backlog* — завдання, обрані на поточний спринт.
- *Increment* — робоча версія продукту наприкінці спринту.
- *Definition of Done* — пункти з `ACCEPTANCE_CHECKLIST.md`: код за ТЗ, тести пройдено, code review виконано, CHANGELOG оновлено.

**Ризики й заходи:**
| Ризик | Захід |
|-------|-------|
| Розповзання вимог | Нові ідеї потрапляють у backlog, а не в поточний спринт |
| Недооцінка часу | Спринт на 1 тиждень, перегляд оцінок на ретроспективі |
| Один розробник, немає code review | Self-review за чеклистом перед merge |

## 2. Схема версій: SemVer (MAJOR.MINOR.PATCH)

| Частина | Коли змінюється | Приклад |
|---------|-----------------|---------|
| **MAJOR** | Зламна зміна, несумісність (інший формат даних, видалення API) | 1.4.2 → 2.0.0 |
| **MINOR** | Нова функціональність, яка не ламає існуюче | 1.0.0 → 1.1.0 |
| **PATCH** | Виправлення помилок без нових функцій | 1.1.0 → 1.1.1 |

Прикладена історія проєкту:
- `v1.0.0` — перший реліз (завдання, список, нагадування, збереження).
- `v1.1.0` — додано експорт у JSON.
- `v1.1.1` — виправлено помилку сортування прострочених завдань.
- `v2.0.0` — перехід на серверне сховище з несумісним форматом даних.

Попередні версії позначаються суфіксами: `1.1.0-rc.1`, `1.1.0-beta.2`.

## 3. Git-стратегія: спрощений GitFlow

Гілки:
- `main` — лише стабільні релізні версії, кожен коміт позначений тегом.
- `develop` — інтеграція фіч.
- `feature/*` — одна гілка на одну фічу, відгалужується від `develop`.
- `release/*` — підготовка релізу (за потреби; для одного розробника необов'язкова).
- `hotfix/*` — термінові виправлення, відгалужуються від `main`, зливаються в `main` і `develop`.

Формат комітів (Conventional Commits): `feat(scope): ...`, `fix(scope): ...`, `docs: ...`, `chore: ...`, `test: ...`.

## 4. Команди Git

Нова фіча:
```bash
git checkout -b feature/add-deadline-list develop
git add .
git commit -m "feat(deadlines): add deadline list module"
git push origin feature/add-deadline-list
```

Після code review:
```bash
git checkout develop
git merge --no-ff feature/add-deadline-list
git push origin develop
```

Реліз:
```bash
git checkout main
git merge --no-ff develop
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin main
git push origin v1.0.0
```

Hotfix:
```bash
git checkout -b hotfix/1.0.1 main
# ...виправлення...
git commit -m "fix(deadlines): correct overdue sorting"
git checkout main && git merge --no-ff hotfix/1.0.1
git tag -a v1.0.1 -m "Release 1.0.1"
git checkout develop && git merge --no-ff hotfix/1.0.1
```

## 5. Єдине джерело історії релізів
Історія релізів ведеться у `CHANGELOG.md` (формат Keep a Changelog) і в тегах Git. Кожен тег має відповідний запис у changelog та release notes за шаблоном `RELEASE_TEMPLATE.md`.
